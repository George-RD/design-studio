# Visual/browser lens: accessibility

## Purpose

Verify accessibility as experienced in the browser while treating deterministic source/computed facts from the local mechanical snapshot as authoritative.

## Triggers

Load for every browser-grounded Review of public-facing or interactive UI, and whenever evidence indicates contrast, focus, semantics, target-size, form, motion or keyboard risk.

## Required context

Use the current mechanical findings, verified viewport, accessibility tree, rendered states and real interaction. Do not estimate numeric contrast or source structure from screenshots.

## Outputs and handoff

Report browser-grounded findings with severity, affected control/region, action performed, observed result, viewport and relevant WCAG criterion when known. Hand findings to Review aggregation; do not edit.

## Authority boundary

This leaf owns experiential accessibility review. Exact contrast, DOM/source semantics, viewport dimensions and target measurements belong to the mechanical gate. It does not import external accessibility checklists or become a second mechanical authority.

## Failure behavior

If browser/accessibility-tree evidence is unavailable, report the missing evidence and defer the visual accessibility verdict. Do not turn an untested path into a pass.

## Evaluation hooks

Check structure/names, logical headings/landmarks, keyboard order, visible focus, activation semantics, focus trapping/return, form error association, async announcements when needed, reduced-motion behaviour, touch targets, and user control over autoplay/timeouts. Blockers include task/access failures, unreachable controls, invisible focus, focus traps or critical colour-only status; structural/error/touch defects are Quality; minor alternative-text/spacing/motion refinements are Polish.
