# Visual lens: hierarchy and rhythm

## Purpose

Judge what the eye sees first, second and third, how density/attention changes through the surface, and whether responsive composition preserves the intended reading/task order.

## Triggers

Load for browser-grounded Review when hierarchy, spacing rhythm, density, composition or breakpoint behaviour is in scope or visibly weak.

## Required context

Use rendered desktop/mobile evidence, surface goal, current `DESIGN.md`, constraints and relevant mechanical summary. Do not infer exact CSS/token values from screenshots.

## Outputs and handoff

Report visible hierarchy/rhythm findings with viewport, region, user consequence, severity and screenshot evidence. Hand findings to Review aggregation; do not edit.

## Authority boundary

This leaf owns visual hierarchy and rhythm judgement. Exact dimensions, overflow and source/token claims belong to the mechanical gate. It does not import external hierarchy/responsive checklists.

## Failure behavior

If required viewport evidence is missing, do not issue a browser-grounded hierarchy verdict for that viewport. If evidence is ambiguous, state the ambiguity rather than inventing measurements.

## Evaluation hooks

Name the actual first/second/third visual signals; verify primary task/action has the strongest appropriate emphasis; supporting content does not compete equally; density matches importance; mobile is recomposed rather than merely stacked; repeated structures are deliberately identical/different; long surfaces vary rhythm without becoming chaotic. Blocker means the primary task/action is defeated; Quality means flat/chaotic hierarchy or materially weaker mobile order; Polish is local pacing/alignment refinement.
